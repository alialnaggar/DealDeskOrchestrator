# M1.4 GroqCloud versus Gemini: bounded benchmark protocol

**Status:** Adapter implementation and offline verification in progress. No live
provider result is recorded here. Phase 1C is pinned at
`90c0bc8e285ee69262c7db826b786096a77ad004` in a separate checkout.

## Models and boundaries

- GroqCloud `openai/gpt-oss-120b`: Chat Completions with local function calling;
  a separate strict JSON-schema final request because Groq does not combine
  tool use with Structured Outputs in the same call.
- Gemini `gemini-3.8-flash`: `generateContent` with local function declarations;
  a separate JSON-schema final request for a comparable protocol.
- The only callable functions are M1.2's `inspect_line_supply`,
  `inspect_fulfillment_paths`, and `inspect_evidence_record`. LangGraph and the
  trusted runtime authorize them, enforce source scope and count calls. The
  model sees restricted line data and returned observations, never DB access.
- At most six model decisions, 12 reserved tool calls, 25 returned records per
  tool and the existing 30-day forward evidence boundary. Each provider
  request has a 30-second timeout, maximum 20,000 serialized request bytes,
  1,024 requested output tokens for a tool decision or 2,048 for a final
  contribution. The opt-in runner spaces calls and stops after a 429.
- A model response is untrusted even if provider JSON-schema mode succeeds.
  Runtime validates contract shape, identity, line permission and citations
  against completed authorized tool results. A proposal stays unverified.

The standard-library HTTP adapters read `GROQ_API_KEY` and `GEMINI_API_KEY`
only from process environment. No credential is copied to graph state, the
ledger, the report, routine CI, or tracked files. `.env*` and benchmark
`results/` are ignored. Local keys must be supplied by a secure execution
environment; no setup claim is made until that is verified. Live tests and
benchmark execution require an explicit `--live` option, isolated PostgreSQL
databases and the pinned checkout. Do not enable paid billing. Google notes
that its free-tier submitted content may be used to improve its products, so
use only synthetic thesis evidence.

## Reproducible trials and their limits

The currently pinned actual reader fixtures give **two** relevant cases:

1. `stock_then_confirmed_receipt` (`00000000-0000-4000-8000-000000010001`):
   binding stock plus inbound meets the requested date. The eligibility gate
   should skip AI. This measures gate safety, not model quality.
2. `offer_without_supplier_commitment` (`00000000-0000-4000-8000-000000030001`):
   a conditional offer with no binding receipt. AI may investigate and cite
   returned offer evidence. Partial delivery is forbidden in this actual case;
   an invented confirmed commitment or split suggestion fails review.

The opt-in runner permits ten independent **repetitions** of the offer case
and two of the binding case per provider. These are 12 paired trials, **not 12
distinct business scenarios**. They can measure stochastic stability,
structured output, citation discipline, tools, latency and usage on the same
pinned evidence. They cannot estimate general business correctness for missing
evidence, no alternative, or unsupported mixed supply. Synthetic offline
contract tests exercise those failure paths, but their expected answers are
not independently accepted Phase 1C business ground truth. Expand the live
case matrix only after building reviewed, compatible fixtures; do not claim
provider superiority from repeated offers alone.

Run sequentially with the same locked code, source pin, fixed decision,
evidence bundle, model-call caps and permission registry. Use unique assessment
threads for each provider/trial. The report records requested/returned model
identity, assessment/source hash, timestamp, contribution or error, citations,
tool calls, token usage and latency. Compare critical incidents first:
fabricated confirmed supply, unauthorized calls or unseen citations. Then
compare valid findings/abstentions and observed timing/usage. Free-tier price
is zero only if the respective account is actually on its free tier; never
infer it from an API key. Account-specific rate limits and tier must be checked
before live requests. Raw secret-bearing requests are not retained.

First use `--offer-repeats 1 --binding-repeats 0` as a connectivity smoke
trial. Inspect its sanitized result and account-specific quotas before a full
paired run. Example opt-in invocation **after** secure keys, DBs, and pinned
rows exist:

```bash
python -m dealdesk_phase2.benchmark_m14 --live --provider groq \
  --output phase-2-implementation/backend/benchmarks/results/groq.json
```

Run the corresponding `--provider gemini` command for the same cases. Routine
GitHub Actions executes only offline mocks and PostgreSQL fixture tests.

## Replay and failure semantics

The authoritative PostgreSQL checkpoint records a model request reservation
before network I/O, then an append-only sanitized completion containing the
validated action, usage, version and timing. A completed decision can replay
without a second API charge or a new tool budget. An interrupted reservation
has uncertain remote completion and must stop; it is not automatically sent
again. A 429, unsupported feature, malformed response, invalid citation or
tool failure is recorded as incomplete AI assistance. The original fixed
assessment and its human routing remain intact.
