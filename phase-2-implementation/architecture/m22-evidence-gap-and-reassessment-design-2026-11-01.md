# Proposed Week 4 extension: evidence gaps and reassessment

Typed signatures, write permissions, authoritative ingestion and delivery dates require a separate implementation review. The original [blueprint evaluation gate](../planning/master-implementation-blueprint.md#8-remaining-implementation-roadmap-and-gates) is **not replaced**. Current checkpoint/projection [audit](../evaluation/m22-wp2-capture-audit-2026-11-01.md) is read-only and WP2 is still open.

## A. Required Week 4 **design**: six bounded gap reports

Proposed `EvidenceGapV1` *review projection*, not an AI claim of a new rule: `version`, `assessment_id`, `phase1c_run_id`, `subject_kind` (`original` or separately fixed-checked `candidate`), `subject_id`, `bundle_sha256`, `source_input_digest`, `as_of_at`, `specialist`, optional `line_id`/`customer_id`/`rule_id`, `source_ref` (nullable if a selected source is absent), `scope` (`selected_reader_pool`, `returned_tool_records`, `fixed_result`, `interface_unavailable`), `field_path` (nullable only when the source interface cannot name an exact field), `reason_code` (`missing`, `stale`, `incomplete`, `conflicting`, `unavailable`, `conditional_unconfirmed`, `prerequisite_unmet`), `basis` (`fixed_result`, `returned_record`, `validated_absence_in_bounded_pool`, `interface_limit`, or `model_suggestion`), `evidence_refs`/`rule_ids` (possibly empty; never fabricated), `next_action_code` (allowlisted human request/verify/investigate/seek_source_contract), and `disposition` (`verified`, `suggested_unverified`, `unresolved`). Validate the tuple of pin, deal, run, subject, source hash, cutoff and scope before surfacing; no generic free-text request can become a fixed prerequisite. Keep supporting source dates, returned fields and deterministic rule IDs only when actually available. Reject duplicated/conflicting identities, unknown codes and spoofed provenance.

**Verified** means the trusted fixed result or authorized bounded source explicitly proves the narrow proposition (including a dated staleness result); it does **not** mean global record absence. `interface_limit` reports a known unavailable contract, not a proof that a business source is missing. AI suggestions must be in a separate list, tied to returned observations or a fixed status, marked `suggested_unverified`, never auto-promoted to verified or used to clear/block a fixed rule. `next_action_code` guides a person to request/validate evidence; it does not add a business obligation. A result can carry valid findings *and* gaps; an AI abstention can coexist with verified gaps; execution errors and skipped prerequisites are not abstentions. A gap resolving in a later assessment must not erase the prior finding or overwrite its package.

| Specialist | What the current pinned interface can establish | What it cannot prove / safe report |
| --- | --- | --- |
| Configuration | Fixed per-line status and compatibility `unknown`/`unsupported`, selected product and matching BOM inspection in `m20_specialists._source_records`; exact line/rule when returned. | Missing BOM or absent compatibility record outside the selected pool is not global proof. Unknown compatibility stays unknown; request source/compatibility review only when fixed/returned fields establish the gap. |
| Pricing & Margin | Fixed `cost_evidence_gaps`, fixed pricing rule hits and selected `pricing_line` fields (`standard_cost`, quote/list, margin); identify exact field/line only if the fixed payload carries it. | No margin recomputation, zero cost assumption or invented discount authority. If the payload does not identify a missing field, report bounded unknown with nullable `field_path` and request source-owner clarification. |
| Availability, Production & Fulfillment | Fixed line `unknown`, `conditional`, `pending_production_check`; dated returned inventory/inbound/offer/path evidence. Existing `claim_validation` accepts `no_eligible_evidence_in_selected_pool` or `supplier_confirmation_not_returned` only within completed, exhaustive-enough scoped reads. | A supplier offer is not confirmed supply; no later capacity or delivery date can be promised. A truncated/unread pool cannot prove absence. Keep conditional/unknown status and original vs candidate separation. |
| Credit & Risk | Fixed `commitments_fresh` false, returned profile commitment date/ref and selected dated AR/payment rows (where present). Report stale commitment field and exact profile ref. | No trusted complete-zero AR/payment scope in current pin; zero returned rows **never** establish zero balance. An empty selected pool supports `unavailable`/`incomplete` (if scope known), not clearance. Do not adopt draft Credit v3 or controls 040/041. |
| Policy & Compliance | Fixed selected `rule_hits`, `hard_blocks`, and `per_rule_prerequisites_available=False`; returned selected hit rules support exact `rule_id` only for actual hits. | Per-rule prerequisite declarations and complete non-hit rule coverage are unavailable; report `interface_limit` without inventing a missing document/rule or a policy pass. Hard blocks remain independent of Credit. |
| Approval Routing | Fixed `route_withheld`, `roles_available_from_fixed_interface`, and prerequisite execution; selected required roles only when explicitly returned. | Withheld roles cannot be named or inferred from AI. Report route/role interface limit or exact upstream prerequisite, not an approval request to an invented role; no AI grant or waiver. |

Proposed reviewer shape: versioned `evidence_gaps` under **each original fixed specialist** and, only when its fixed results exist, each **candidate fixed specialist**; separate `ai_gap_suggestions` with original-subject attribution and validation status. A package may show a gap beside a valid fixed finding and beside an AI abstention. Provide count/status and source pointers, not raw model prose, private receipts or unbounded rows. Missing required gap contract or inconsistent source means fail-closed/unavailable, not an empty “no gaps” array. `m22_capture` remains a historical checkpoint observation; adding gap metadata to a **new** package version needs tests and cannot rewrite prior checkpoints.

## B. Stretch Week 4 working implementation: authorized new assessment

**Smallest viable path to investigate, not an approved write contract:** a trusted, authenticated operator submits an evidence-revision request bound to original deal/run, prior assessment ID/source hash, explicit source IDs/fields, asserted effective/as-of dates, provenance, reason and idempotency key. An authorization boundary validates actor/role, allowed source types, original customer/line and field ownership, schema, dates, conflicts and completeness **before** acceptance. User text is not a verified source; a supplied attachment cannot bypass Phase 1C's typed reader and rules. No Odoo/n8n/production writer or new database/queue is approved. Where the pinned reader cannot ingest a category (e.g. Credit completeness or Policy prerequisites), stop as `source_contract_unavailable` and request Phase 1C-owned API/release design; do not inject synthetic completeness into the sealed bundle.

If an *authorized, supported* source version can be read consistently, persist/freeze an immutable, canonical **new source snapshot** and its provenance/fingerprint; distinguish business as-of cutoff, database transaction snapshot and durable source version. Create new Phase 1C run/source version and Phase 2 assessment/thread `V2` with explicit `parent_assessment_id`, `parent_bundle_sha256`, revision request ID, changed source refs, old/new source hashes and cutoff; retain `V1` unchanged and readable. A new transaction read and seal is not sufficient proof of durable immutability unless source versioning or frozen copies are demonstrated. Revalidate the reader's actual source snapshot and run identity before a new assessment; reject equal/stale/conflicting fingerprints, unauthorized edits, changed customer or wrong line. Never mutate the original deal, old sealed bundle, completed checkpoint, receipts or candidate audit.

Initially run **all six fixed responsibilities** on V2 and all eligible six bounded AI stages with new assessment identity and permissions; create a new reviewer package, recompute Routing on the exact V2 subject, and only then consider a V2 candidate with its own fixed recheck. No V1 AI result, validation claim, candidate, approval, held route or tool observation is copied into V2. Old model reservations remain terminal in V1; V2 is an independently authorized new assessment, **not** permission to retry an uncertain V1 send. Enforce per-assessment and cross-version rate/usage policy, access audit and duplicate-submission protection; idempotent duplicate V2 submission must return the same authorized V2 identity without another send. Selective reruns are deferred until a tested dependency graph and source fingerprints prove that unchanged prerequisites, Credit/Policy, candidate and Routing cannot become stale. Human approval/customer acceptance remain separate, version-bound decisions; V1 decisions never approve V2.

Offline negative gates before calling stretch work implemented: wrong actor/source/subject/date, conflicting revision, duplicate key, unsupported Credit/Policy input, stale/unchanged snapshot, preflight failure, V1 reserved/uncertain send, V2 interruption/restart and no duplicate V2 send, changed source after seal, six full V2 fixed/AI outcomes, conditional supplier offer, old vs new reviewer separation and no automatic approval. Source-first reviewer answers and held-out case identities remain invisible to both versions.

## Feasibility, effort and gate

Estimates are **engineering working days, not a four-week promise**; assume one developer, existing disposable PostgreSQL + Python/LangGraph, stable pinned reader, offline doubles, no new infrastructure or hosted calls. WP2 receipt/failure reconciliation is a prerequisite for any V2 sender/recovery work.

| **A — required Week 4 design** | 1–2 days (including source-field audit, contracts, threat review, tests/acceptance plan) | This document is an initial proposal; review exact fixed payloads, source-owner interfaces and reviewer contract with Ali before coding. Does not implement working reassessment. |
| **B — stretch working reassessment** | 6–12+ days **after** A/WP2, assuming an authorized versioned source-ingestion interface exists; otherwise unestimable | Auth/validation 1–2; durable source version and lineage 2–4; full six-stage V2 + checkpoint/no-replay 2–4; offline failure/regression 1–2. | **C — deferred** | Separate plan/estimate | Source ingestion/reader extension if Phase 1C cannot consume added evidence, Credit v3/pin adoption, general candidate types, selective reruns, Next.js submission UI, hosted reliability/paid APIs and deployments. Evaluation still requires accepted source-first answers, matched baseline, measured latency, reviewer fidelity and governed safety. |

Example: N01/UC02's selected Credit profile has stale commitments and no returned AR/payment. Report the **verified** stale-profile field with its dated profile ref, plus an **unresolved** complete-ledger interface limit; no zero-exposure claim. A human may request updated commitments, but unless the owner provides an authorized dated source version consumable by the pinned reader, there is no V2 reassessment. If a compatible version is later approved, V2 gets a new seal/thread and full six fixed + eligible AI checks, leaving V1 abstention and uncertain sends intact. No clearance or approval follows automatically.
