# Bounded Fulfillment correction prototype — implementation note

**Status (25 October 2026):** Implemented and validated locally against isolated PostgreSQL; **not pushed or PostgreSQL-CI validated**. This is a separately identified offline engineering prototype, not a reinterpretation of the M1.8/M1.9 live trials or evidence of live model improvement. Phase 1C stays at `90c0bc8e285ee69262c7db826b786096a77ad004`.

## Exact scope and trusted flow

The existing fixed original assessment and Fulfillment investigation execute first. The first model contribution is recorded, including its sanitized original action, execution status, model-turn count and pinned assessment/run/subject/source identity. At most one same-specialist V3 binding revision may follow, and only when:

- The original fixed assessment and existing single-line shortage eligibility remain valid; partial delivery is permitted.
- The first contribution was a rejected V3 binding proposal. A valid abstention, V2 claim, provider error, forged citation, wrong identity or denied tool call is terminal.
- Either (a) one or more quantity strings have only a positive integral ASCII-decimal formatting error (e.g. `"8.000"`), and a **temporary classification-only projection** passes all the other V3 shape and returned-binding-source checks; or (b) a structurally valid proposal fails the pinned fixed verifier with the **exact** quantity-total `ValueError` below and actually differs from the requested total.
- The same evidence is available and at least one of the existing six model decision turns remains. No extra tool invocation is allowed on revision; the previous 12-call tool ledger, per-response 25-record limit and 30-day forward horizon stay in force.

The pinned `phase1c_candidate.review_partial_delivery` raises `ValueError("Delivery slices must account for every original unit and line")` when its per-line sum differs. This exact message and its source/behavior were checked against the pinned Git object; the separate classifier recognizes **only** that message. The first precheck uses the existing read-only `Phase1CAdapter.verify_candidate` only to classify this rejection. A successful precheck declares nothing valid: the normal candidate graph still constructs the sole published candidate and performs the complete read-only Phase 1C verification and six deterministic mappings. Unknown or changed exceptions never create feedback. No other fixed rule is reimplemented or overridden.

Feedback `fulfillment-correction-v1` supplies a stage, fixed constraint code, safe field path(s), original requested and model-proposed totals where applicable, bounded returned reference IDs, and remaining model turns. It supplies no corrected slice, raw verifier exception, database row, hidden evaluation answer or new authority. The revision uses the original Groq `openai/gpt-oss-120b` adapter in an opt-in **no-tool final JSON turn**, or a scripted offline model. Neither the provider nor the Phase 1C business rules change.

## Persistence, replay and review

`fulfillment_correction` is an additive original-graph checkpoint slot with a version, trusted identity/provider/model, ordered first/revision attempt records, first rejection code, safe feedback and revision status. The first raw model action is bounded to 16,384 UTF-8 bytes for this additional audit; oversized/nonserializable content is ineligible for correction. The revision is reserved in PostgreSQL **before** calling the model, with a distinct deterministic attempt ID. Its sanitized response is checkpointed before fresh V3/returned-source validation. A saved completed response can be revalidated on restart; a reserved request with no checkpointed response is **uncertain and terminal** (no automatic resend). Source/model identity mismatch stops replay. Completed tool evidence is checked against assessment/run/subject/line/source identities before reuse; no extra tools are issued.

The original AI output and its fixed or formatting failure remain in audit; a revised contribution is a new unverified hypothesis. The existing one-candidate graph validates and verifies only the final eligible contribution. On second failure or interruption the original fixed assessment survives, routing is not upgraded, and the reviewer sees no fabricated support. Reviewer output shows only the bounded correction stage/status and verified candidate outcome, never raw rejected model text. `evaluation_m18.capture_trial` records an additional, separately named `correction_prototype` field; historical M1.8/M1.9 source observations and answer sheets are untouched.

## Tests and limits

Local Python 3.12 environment in `/tmp/opencode/dealdesk-test-venv` uses the existing `backend/requirements-m1.1.lock` (no system-wide install). For database tests, the Ubuntu PostgreSQL 16.15 packages were **extracted** (not installed) under `/tmp/opencode/dealdesk-pg16`: a user-owned instance used a private Unix socket, disabled TCP, and separate disposable fixture and checkpoint databases. The Phase 1C checkout in `/tmp/opencode/dealdesk-phase1c-pinned` was detached at the unchanged exact pin. The pinned schema, reference fixture rows and compiled commercial rules were loaded into the isolated fixture database. The final clean-database `python -m unittest discover -s phase-2-implementation/backend/tests -p 'test_*.py' -v` run returned **98 tests, OK, zero skipped**, in 17.716 seconds; local output is `/tmp/opencode/dealdesk-pg16/full-test-final.log`. This includes PostgreSQL correction tests for `"8.000"` and B05 overcount, saved response and reviewer handoff, a reserved-response interruption followed by a reopened PostgreSQL saver, plus the existing checkpoint and candidate regressions. No live model calls were made: the Groq-request test uses a mocked provider.

The first database run exposed an incorrect *test assertion*, which searched the entire reviewer package for `"8.000"` even though the original fixed reader correctly reports its own `Decimal('8.000')` available quantity. The assertion now targets the rejected model quantity in the published candidate and correction summary without altering the original fixed finding. An attempted rerun on the previously used database failed the fixtures' duplicate-source/fresh-database guards; both disposable databases were recreated for the final passing run. The user-owned database does not use or alter the VM's Odoo, n8n or other services. No GitHub Actions CI run is claimed; CI's PostgreSQL service uses a different server version (18). Before integration, run the full two-checkout workflow in `.github/workflows/phase2-m1-contracts.yml` when authorized/available, and inspect any platform or server-version differences. Do not run a live model trial without separate approval.

This prototype does not add general retries, candidate search, substitute/mixed-offer verification or business approval. A first fixed failure other than the exact quantity-total rejection remains terminal; valid candidates are still unreserved and subject to customer acceptance and human review.
