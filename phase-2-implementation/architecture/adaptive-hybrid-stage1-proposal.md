# Adaptive hybrid specialist investigation — Stage 1 approved direction, implementation proposal

**Status (26 October 2026; provider direction updated 31 October): target direction and D1–D4 below approved for design; implementation, activation and live testing NOT authorized.** Groq `openai/gpt-oss-120b` is the provisional development comparison model; a paid OpenAI API model is an intended future production option, not selected/connected/paid by this design. The existing iterative runtime stays **unchanged as a comparator**. Gemma is discontinued and not a comparison arm. No M2.0 work follows from this proposal. Phase 1C remains at `90c0bc8e285ee69262c7db826b786096a77ad004`.

**Owner decisions governing this version:** **D1** one counted, provenance-logged `inspect_line_supply` prefetch; dated-path inspection model-directed; no baseline/answers in pack. **D2** reject leading-zero and every other noncanonical proposal quantity, retaining raw output and rejection reason. **D3** explicit typed submit intent then separately reserved structured final by default; no no-tool/`READY` shortcut; one-turn mode only with provider-specific proof. **D4** at most one model-authored revision only for narrowly classified format, required-field or total-quantity mismatch, with safe feedback; never give a corrected quantity/date/source mapping/expected answer; unsupported source-to-slice, conditionality and unknown verifier failures never initiate revision. **Evaluation decision:** zero-tolerance safety gates are mandatory; no numerical business-quality threshold until a representative set and fixed baseline are defined, and thresholds must be predeclared before hosted comparison. These approvals do **not** approve coding or provider requests.

## Evidence and design boundary

- Hosted Groq has completed authorized-tool-to-structured-final and accepted *returned-record* citations on R03 ([M1.4](../backend/benchmarks/m1.4-gated-smoke-results.md)); its M1.8 four binding proposals failed whole-unit validation before construction ([M1.8](../evaluation/m1.8-measured-results.md)), and M1.9 B01 abstained while B05's 11+18/18 proposal was fixed-rejected ([M1.9](../evaluation/m1.9-contract-and-output-results.md)). **No live Groq fixed-supported binding candidate.** Its current parser treats any no-tool response as ready (`live_models.py::_parse`): a literal `READY` was not established by those records.
- Preserve the six **distinct** responsibility mappings: Configuration Validator; Pricing & Margin; Availability, Production & Fulfillment; Credit & Risk; Policy & Compliance; Approval Routing. Currently only Fulfillment has model/tool AI; the other five are fixed mappings. Do not claim six AI agents are implemented. Phase 1C owns authoritative reader, rule outputs and candidate checks; no model or Phase 2 prompt computes approvals, booking, customer consent, reservations or a binding delivery promise.

## 1. Typed provider-independent action and result contracts

Propose `SpecialistActionV1` as a strict discriminated union; exactly **one** action per model decision, with no prose-as-control, no unspecified fields and no model-supplied trusted identity:

| `kind` | Required model fields | Resulting trusted transition |
| --- | --- | --- |
| `inspect` | `tool_name`, typed `arguments`, `purpose_code` (bounded enum, diagnostic only) | Validate specialist permission, line/subject and budget; reserve and execute one read-only tool; append completed observation or stop on denied/failed call; return to decision. No multi-call batch/parallel execution. |
| `submit_proposal` | `submission_kind` (supported capability enum; initial Fulfillment: `binding_partial_delivery`), `payload` if safely carried in this provider mode | Stop tool loop. Validate a structured *unverified* proposal via the domain validator; construct/recheck only if eligible. If this adapter uses a separate final request, decision contains **intent only** and the final must contain the matching kind/payload. |
| `submit_finding` | `payload` containing typed scoped claims and uncertainty (or intent, when separate final is needed) | Validate claims and citations; renderer exposes only accepted claims, never free text or rejected claims as fact. No candidate. |
| `abstain` | Typed `reason_code`, `scope`, optional `missing_evidence` and audit-only explanation (or intent) | Complete without candidate or favorable finding; preserve original and human review. Distinguish insufficient evidence, unsupported capability, authorization limit and model uncertainty. |

Trusted runtime wraps each action with schema version, assessment, original/candidate subject, specialist, sealed bundle/source digest, model/provider, stage/ordinal and attempt ID. Model fields never set these values, `verification`, candidate ID, approval, routing or tool permissions. Each specialist supplies a **domain-specific** input, permitted-tool registry and payload validator behind this small common union; do not turn the six into one vague generic business schema. Per-specialist actions with no available tools can submit or abstain, but designing future specialist tool scopes is **outside this stage**.

For the portable **intent-only decision** mode, illustrative parsed actions are `{"kind":"inspect","tool_name":"inspect_fulfillment_paths","arguments":{"line_id":"<authorized-line>"},"purpose_code":"check_dated_path"}` and `{"kind":"submit_finding"}`. The latter records an intent, **not** a finding: the following separately reserved final must return a schema-constrained `{"kind":"submit_finding","payload":{"line_id":"<same-line>","claims":[...],"uncertainty_reasons":[...]}}`. The final is validated against the saved intent and trusted line; `inspect` is forbidden in that phase. A provider capable of safe one-request submission may instead return the complete latter union in a tested, versioned mode. JSON examples are contract illustrations, not actual model evidence or business answers.

Use an explicit decision/submit transition. Portable default: model decision offers native functions `inspect_<authorized_name>` and `submit_proposal`, `submit_finding`, `abstain` with bounded, typed intent arguments. The adapter accepts exactly one native function call whose name and arguments parse into the above union. Only `inspect` executes a local evidence tool or consumes the 12-call **evidence-tool** budget; `submit_*`/`abstain` are typed model decisions and count toward the **model-decision** budget, never the evidence ledger. For `inspect`, return the authorized result and decide again. For `submit_*`, checkpoint `submission_intent(kind)` and make a separate **no-tool, schema-constrained final** request for the matching payload; no tool is permitted on final. Mismatched/empty intent, arbitrary no-tool text (including a bare `READY`), multiple calls, wrong kind, or incomplete final is an error, **never implicit permission to finalize**. An adapter may optionally use a single-turn, complete typed submission when that provider's actually tested constrained-union contract supports it; both paths produce the same checked `SpecialistActionV1` and outcomes. Do not assume concurrent native tools and strict JSON schema work together on any provider. This default can cost a handoff request; avoiding it is not worth an ambiguous handoff or weaker final shape. A schema-valid model response is still untrusted domain content.

Proposed LangGraph conceptual states: `fixed_original -> investigation_start -> pack_reserving -> pack_completed -> decision_reserved -> action_saved -> {tool_reserved -> tool_completed -> decision_reserved | submission_intent_saved -> final_reserved -> final_saved} -> contribution_validated -> {candidate_unverified -> fixed_checked/fixed_rejected | no_candidate} -> reviewer_prepared -> terminal`. Separate error/uncertain-terminal edges from **every** reserved external call. Existing LangGraph stays selected; this is not a proposal for a custom orchestration engine.

## 2. Initial evidence pack: bounded, citable, but not an answer key

Build **after** successful original fixed mapping and eligibility, from the already sealed selected Phase 1C context. **D1-approved first Fulfillment pack:** the trusted result of one scoped `inspect_line_supply(line_id)` (same authorized projection, 25-record ceiling, 30-day forward horizon), plus the restricted original line/customer constraints and the allowed fixed Fulfillment status/quantity-by-request-date. No `discover_partial_delivery` output, baseline candidate, normalized ideal split, answer sheet, verifier feedback or recommended schedule is included. Dates/quantity/status fields present because they are actual source or fixed facts, not calculated candidate answers. `inspect_fulfillment_paths` remains an **optional model-directed** inspection when dated path support is needed; a binding proposal is not eligible without a complete `eligible_binding` paths observation. For a simpler bounded finding, the model need not request it. A future alternate pack recipe is a separately versioned experiment, not an invisible model-specific shortcut.

Pack schema proposal: `pack_version`, `specialist`, `subject/line`, `as_of_at`, `catalog/policy identifiers`, `phase1c_run_id`, `bundle_sha256`, `source_input_digest`, `permission_version`, `recipe_version`, `record_limit/horizon`, `observations[]`, `coverage`. Internally these identity fields are trusted and hashed; the model sees only the restricted context, explicit coverage and source projections necessary to reason. For each observation persist trusted tool call ID/args, completion status, evidence category, bounded record projections with `category:id`, dated fields, provenance (`returned_by`, relevant source/status/commitment), `returned_refs`, `binding_options`/conditional estimates *only if that authorized call actually returned them*, and exact truncation/gap markers. No arbitrary database row, secret, raw error, hidden answer or full sealed pool is exposed.

`coverage` states which *selected-pool line/categories and date horizon* were inspected, as-of time, per-tool record cap, `more_in_sealed_pool`, unsupported mixed-path classification, missing/unknown status, and whether the claim is limited to returned records. Unknown/truncated/conditional is **not** absence or binding availability. A returned offer's validity/lead days are not a confirmed receipt or delivery date. If the pack call is denied, interrupted or truncated, record that rather than silently filling from the database. Never pass as-of data as proof that no other data exists.

**Citation eligibility:** prefetch is a real invocation of the same authorized facade and completed returned-reference ledger as model-selected calls, with `origin=trusted_prefetch`, line/scope/identity, exact records shown and call/response digest. Only its **completed, actually exposed** references can be cited. An ID in the sealed pool or a reserved/incomplete tool event is not citable. Citation validator checks exact assessment/subject/line/source digest, category/id and returned projection/field; later tool reads must satisfy the same test. Rule/fixed-finding citations have a **separate typed namespace and fixed-result identity**, never impersonate returned source rows. The model can cite a source observation without promoting its conditionality; binding source-to-slice and supply validity require further checks below.

## 3. Optional model-directed inspection and bounded resource policy

Model sees the pack, a truthful list of **currently authorized** tools, their typed arguments, scope, coverage and remaining budget. Preserve current `inspect_line_supply`, `inspect_fulfillment_paths`, `inspect_evidence_record`; the latter can inspect only a previously exposed line-scoped record. Runtime validates arguments against `TrustedToolScope` regardless of provider schema, reserves the call, returns at most one bounded response and logs exactly what was returned. The pack consumes **one counted call** from the existing 12-call budget, not a free unlogged read. Keep 25 records/tool response and requested-date +30-day forward limit; no pagination/completeness fiction. No parallel calls, web, free-form SQL, write tools or cross-specialist permissions. An unnecessary repeated call may return a saved result if exact idempotency contract permits, but may not silently consume a new unbounded budget or return new data. Stops include tool limit, turn limit, token/latency envelope and unsupported evidence. A stopping condition yields an explicit error/abstention, never a synthetic verified candidate.

**Proposed pilot ceilings:** <=6 model decision actions total, <=12 counted tools including prefetch, <=1 final submission request, <=1 explicitly eligible correction request and <=1 constructed candidate (current M1.7 scope). The correction has its own ordinal; it is not an uncounted extra loop. These are ceilings, **not quotas to use** or assurances that one candidate suffices generally. Reserve slots at investigation start and document exact inclusive counts for decision, final, pack, correction and model-facing token budget; measure actual counts before changing limits. Per-provider stage output caps/timeout and project quotas belong to adapters/config and remain separately approved for hosted tests.

## 4. Validation, evidence truth and raw/canonical records

1. **Action/schema boundary:** closed union, single allowed action, bounded payload bytes/arrays/strings, valid IDs/typed dates; reject unknown field or wrong stage. A model-provided source reference cannot enlarge a trusted scope.
2. **Claim boundary:** reuse M1.6 typed source observations, fixed references, conditional possibilities, bounded evidence gaps and nonactionable ideas. Check cited field/value/scope against completed exposed projections or exact pinned fixed finding. Retain rejected original claims and reason; reviewer wording is generated from accepted claims and fixed results, never unvalidated free-text notes. `abstain` cannot carry a hidden favorable finding.
3. **Binding proposal boundary:** initially only existing single-line/two-slice, partial-allowed, binding-only M1.7 support. **D2 canonical grammar:** quantity is an ASCII string matching `[1-9][0-9]*`, with a bounded maximum length before integer conversion; reject `"08"`, `"00"`, `"8.000"`, fractional/signed/Unicode digits and JSON numbers. No leading-zero normalization. Each ISO date must be canonical; distinct `source_refs` per slice must have actually been returned. Require a complete, untruncated `eligible_binding` paths result for the line. Supplier offer or unsupported mixed classification cannot become a confirmed source. **Access is not per-slice support:** before construction validate exact returned IDs and canonical shape; only Phase 1C `verify_candidate` may establish dated, cumulative and source-to-slice support. Compare each proposed slice's date/quantity/refs to the pinned verifier's checked slice trace before reporting supported citations. Without that trace, withhold support rather than calculating availability in Phase 2. **Stage 2 offline pinned discovery:** B01's returned stock option arrives Sep 3, but Phase 1C validates an 8-unit Sep 4 proposed slice using it (`phase1c_candidate.py::assess_reader_slices` uses option arrival `<=` slice date). Exact option-date equality would reject a verified candidate, so it is not the provenance rule.
4. **Audit boundary:** save a bounded raw model action/final (including original numeric text and citations) separately from the parsed **unchanged** canonical-accepted representation, validation outcome and fixed recheck. D2 forbids accepting and canonicalizing a noncanonical string. The current comparator's `candidate_contract.py` converts otherwise accepted digit strings with `str(int(qty))`; do **not** alter that historical path or its measurements. The hybrid version rejects leading zeros before any canonicalization; for accepted strings the numeric representation is unchanged. Keep original raw text and explicit `quantity_noncanonical`/other rejection codes. Never turn a rejected V3 quantity into a candidate as a side effect of parsing. Trusted candidate ID and approval status come only from the orchestrator. Source-to-slice failures and `fixed_rejected` stay in audit and nonfavorable reviewer view. `supply_supported_unreserved` still leaves customer acceptance/approval pending.

## 5. Immutable start snapshot and exact restart table

Persist `InvestigationStartV1` **once before any pack call or model send**, bound to a fresh assessment and fixed original: Phase 1C pin and adapter/reader versions, run/deal/subject/line, selected as-of and seal/source digests, relevant fixed-output digest, eligibility/prerequisites, restricted input, authorized tool/field registry and permission version, pack recipe, action/final/validator versions, ceilings, and one chosen provider/model/adapter/config/prompt-policy version. Freeze a canonical serialization/hash and version; do not recalculate `remaining_calls` into a new prompt on recovery. The completed pack is then frozen as `EvidencePackV1` plus exact completed tool-ledger events. For **each** model request persist stage/ordinal, **byte count and SHA-256** of the exact serialized request body (not credentials or raw request text), adapter/version, result status and bounded sanitized action/usage; a resumed *completed* action reads the saved action. Retain sealed inputs and canonical deterministic reconstruction and assert the digest matches before use; do not persist raw secrets, thought text or signatures by accident. A provider that needs signed native-history replay requires a separately reviewed secure exact-history retention policy; otherwise use independent requests.

| Restart point | Required behavior |
| --- | --- |
| Before pack/tool/model reservation | Verify frozen identity/versions and pool seal; continue only if unchanged. No hidden new source refresh. |
| Reservation durable but no completed result, including crash or timeout with uncertain processing | Mark uncertain terminal; do not auto-retransmit or reprefetch that reserved call for this assessment. Preserve original; a new investigation requires explicit new identity/authorization. A known HTTP error is also terminal and classified by its sanitized status, not called a model response or retried. |
| Completed pack or tool result saved | Reuse the exact saved observation, returned refs and budget; no new source read to manufacture citations. |
| Completed model decision/final saved | Resume from saved validated action/raw final with unchanged version and digest; no provider call. |
| Verifier in progress / candidate checkpoint interrupted | Re-run **only read-only** verification if its result was not committed and the exact sealed source/pin still match; candidate identity and original remain immutable. Never replay a business write. |
| Mismatch (source, version, provider, permission, request digest) | Fail closed with explicit stopping reason; never weaken digest checks, silently switch provider, or change prompt mid-thread. |

Use existing PostgreSQL LangGraph checkpoint and append-only ledgers, not a second state store by default. The current ledgers are **single-caller** oriented (`model_attempts.py`); Stage 2 must prove atomic exclusive claim/single-worker ownership (or design a transactional compare-and-set before parallel workers are allowed). A checkpoint reservation is durable before outbound HTTP; fsync semantics for a separate file are not a substitute for transactional DB checkpoint durability. A read-only API call can still have an unknown provider charge; a `500` does not imply zero tokens. Developer-owned separate tests may use new assessments; do not resume a terminal/uncertain one to obtain a nicer output.

## 6. Revisions: explicit, bounded, auditable, no answer leakage

**D4-approved classes, at most one new model-authored submission:** (a) `quantity_format` where an otherwise scoped proposal contains a noncanonical quantity string; (b) `required_field_missing` where a recognized proposal/typed claim has an allowlisted missing *non-identity* field and all present references pass scope/provenance checks—never infer missing binding or date support; (c) `quantity_sum_mismatch` when a known fixed rejection specifically attributes the total to the model's quantities. For the initial test allowlist, `tradeoff_code` or typed claim `scope` can be reported missing; missing `line_id`, a missing/malformed source reference, ambiguous/missing delivery date or quantity, mismatched identity, unsupported binding or missing complete paths are **not** safely classifiable and are terminal until separately reviewed. Expand the allowlist only by a versioned, reviewed design decision; D4 is permission, not an obligation to revise every error. Format-only classification must not treat other concurrent source/date/identity errors as format-only. Revision is **not** an automatic fix, a second tool exploration, a retry of failed HTTP or a conversion of a model error into an abstention.

If and only if one allowed class is demonstrated, relevant evidence is still complete/sealed, no approval/commitment exists and an unused revision slot is durably reserved: checkpoint rejected bounded raw, exact validator/fixed outcome, feedback version and remaining budget. Feedback may contain only `constraint_code`, allowlisted `field_paths`, stage, generic contract text, and original deal/request identity already visible to the model. It must **not** provide a corrected quantity, missing amount, computed target, proposed total, source/date mapping, hidden baseline, expected answer or raw verifier/provider exception. Reuse frozen authorized observations only; no additional tool. A new full model-authored proposal or abstention gets its **own** separately reserved no-tool structured request and raw audit. Re-run the same shape/provenance checks and exact pinned fixed verifier on a new proposal; record both distinct submissions and their fixed/reviewer outcomes. Unsupported source-to-slice, conditional offer/mixed source, missing paths, unknown verifier failure, source mismatch, exhausted budget or second rejection is terminal. The comparator's offline `fulfillment_correction.py` currently includes original/proposed totals in some feedback and constructs a format-only *diagnostic* projection; it remains unchanged, but its feedback is **not reusable as-is for hybrid D4**. No hosted correction success is established.

## 7. Adapter and deployment boundary

Define a small `ProviderAdapter` interface conceptually: `build_decision(frozen_input, observations, authorized_tool_specs, stage_settings) -> request`; `parse_decision(response) -> strict action`; `build_final(intent, same frozen context) -> request`; `parse_final(response) -> typed payload`; `build_revision(feedback, same frozen context) -> request`; `safe_usage/finish/error_shape`; `canonical_request_digest`. Transport never invokes a business tool. Orchestrator validates each returned action and owns tools, checkpoint, claims, candidate, verifier and reviewer. All model-visible domain instructions, identifiers, schema versions and tool definitions come from versioned **shared specialist contracts**; adapter handles only wire serialization, native function/text/JSON mapping and provider stage policies. Tests compare semantically equivalent model-visible evidence across adapters, not byte-identical provider wires.

- **Groq:** provisional development adapter for `openai/gpt-oss-120b`. Use named `submit_*` decision functions instead of inferring no-tool `READY`, followed by a strict JSON-only final where needed; retain 0 temperature and measured usage. Provider schema compliance does not replace trusted whole-unit validation.
- **Future OpenAI API:** separate paid approval, key/data policy, explicit model/version selection, request budgets and tested native tool/strict-final support. Never assume Groq's GPT-OSS model ID, JSON-shape behavior, price or tool semantics carry over merely because both use OpenAI-style APIs. The business validators and sealed evidence contract must remain unchanged. Keep per-provider attempts on separate fresh assessments; no mid-assessment provider switch.

## 8. Paired evaluation specification, not live authorization

Compare **A: current unchanged iterative** and **B: adaptive hybrid** on identical sealed case/source hashes and Phase 1C pin, using Groq on both arms. Neither arm receives answer sheets, baseline schedules, rejected previous trial outputs or reviewer correction; both use the same allowed source pool, trusted tool functions, 12-call/25-record/30-day ceilings, candidate verifier and review gate. Hybrid's one counted prefetch must appear in totals. Decision/final requests and stage caps differ by design: publish both policies, actual prompts, max budgets and denominators rather than call the comparison a one-variable prompt test. New assessment/thread per arm/repetition; predeclare trial count, sequence/randomized balanced order, start/stop rules, credential/quota checks and approvals **before hosted calls**. Do not recycle old M1.8/M1.9 trials as the matched B arm.

Evaluation strata: (a) B01–B05 binding positives and N01–N04 negatives with preserved developer/supervisor provenance, not five independent business families; (b) R03 conditional offer, R01 fixed-skip and no-action cases; (c) **new** sealed uncertainty/contradiction/truncation, misleading conditional offer, wrong-location/date and two cases where only additional authorized `inspect_fulfillment_paths` or `inspect_evidence_record` can support a sound finding, predeclared and independently source-reviewed where possible. Stage these as a proposal; no source fixture or Phase 1C change is authorized here. Fault-injection/restart tests remain a separate **offline engineering stratum**, never counted as hosted model successes. Deterministic `discover_partial_delivery` is a hidden-from-model rule-only comparator on the same sealed inputs. Semantic review should be blind to arm/provider where practicable and should separate source-first developer acceptance from external independent acceptance.

Record every attempted case/arm/repetition including failed HTTP and no-response: eligibility/skips, decision/inspect/submit/abstain transitions, exact source IDs returned and cited, per-slice date/source provenance, raw/validated/rejected claims, proposal quantity/date correctness, candidate construction vs fixed result vs reviewer safety, missed supported options and inappropriate commitments, correction use, changed-original or unauthorized accesses, incomplete/uncertain restarts, model requests, tool/prefetch calls, input/output/thought tokens when available, elapsed time, rate limits and monetary cost **only if actually measured**. **Mandatory zero-tolerance safety gates in tested cases:** no unauthorized access or hidden-answer exposure; no unsupported confirmed date/supply, false favorable commitment, or unvalidated AI prose in reviewer output; no original mutation, silent proposal repair, unverified candidate promoted to verified, autonomous approval/reservation, or uncertain-send replay. A violation halts progression and requires root-cause review; zero observed violations is **not** a population guarantee. **Business-quality metrics, not automatic safety gates:** independently reviewed fixed-supported candidate rate, appropriate abstention, correctly scoped claim/citation rate, useful verified options beyond fixed baseline and missed opportunity. Report by stratum, attempted denominators, raw errors and uncertainty; do not invent numeric targets or gate on the successful-subset alone. Efficiency metrics (requests, calls including prefetch, p50/p95 when supported by sample size, tokens, time) are secondary. First freeze a sufficiently representative, source-reviewed case set and its rule-only baseline, **then** propose numerical quality thresholds/sample sizes and obtain owner sign-off **before** any hosted paired comparison. No post-result threshold fitting.
