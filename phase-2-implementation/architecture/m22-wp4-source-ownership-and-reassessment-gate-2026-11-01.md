This is a proposal for source-owner/security review, **not approval** of a new writer, authentication service, model call, pin or business rule. The earlier [Week 4 V1/V2 outline](m22-evidence-gap-and-reassessment-design-2026-11-01.md#b-stretch-week-4-working-implementation-authorized-new-assessment) remains the intended business flow; this audit determines what is actually possible today.

## Source inventory, owners and permission findings

All Phase 2 specialist evidence is pinned through `Phase1CAdapter.read_original` and named **read-only** tools; `verify_candidate` separately rereads original and candidate in another **read-only** transaction and rejects changed original evidence. Neither path accepts or versions a new business source. `read_run` selects SQL rows by run/policy/catalogue/as-of; its historical mode additionally **requires explicit frozen credit and operational resolvers**, which the current Phase 2 adapter does **not** supply. The repository has **no authenticated source owner, actor-role mapping, source write API, verified document intake, or immutable operational revision ledger**. “Owner” below is a *domain steward to confirm*, **not a granted role or a claim about Odoo/Salesforce**. A salesperson may request investigation; they cannot self-certify a supplier, warehouse, financial or policy fact. Existing SQL checks/columns constrain values but do not authenticate provenance, authorize actors, or guarantee durable history.

**Context distinction:** `as_of_at` is a business cutoff; PostgreSQL `REPEATABLE READ READ ONLY` freezes visibility **inside one transaction**; `data_snapshot_ref` names a run context, and `source_input_digest`/`bundle_sha256` bind *selected content*, not the complete database or durable version of mutable sources. A new as-of time, transaction or seal alone does not create an immutable source release. `verify_candidate` deliberately rejects changed original selected evidence in a new read rather than refreshing it. The checkpoint database stores LangGraph run state, **not** source-authorized business rows. Existing restricted test-role preflight (`backend/tests/verify_b05_restricted_preflight.py`) explicitly denies business-table UPDATE and schema CREATE; no write privilege is inferred from a disposable test administrator.

## Proposed typed intake envelope — contract design, not an executable endpoint

Separate **untrusted proposal** from an **authority-signed acceptance**. All examples below are shape definitions; `actor_id`, `asserted_role`, `source_owner_id` and document links in a submitted request are **claims**, not authorization. Do not permit clients to provide accepted status, revision ID, trusted timestamps, new run ID, model scope or reviewer decisions.

```text
EvidenceIntakeProposalV1 {
  version: "m22-evidence-intake-proposal-v1",
  request_id: UUID, idempotency_key: opaque bounded string,
  parent_assessment_id: string, parent_phase1c_run_id: UUID,
  parent_original_deal_id: string, parent_bundle_sha256: SHA256,
  parent_source_input_digest: SHA256, parent_as_of_at: RFC3339,
  gap_version: "m22-evidence-gap-v1", gap_identity: canonical digest of an
    independently reprojected *original* verified gap or interface limit,
  specialist: enum of six, evidence_category: source-owned enum,
  source_id: exact selected record ID or explicit proposed-new-source marker,
  customer_id?: string, line_id?: string, field_path: allowlisted per category,
  proposed_value?: typed schema-specific value, document_ref?: bounded opaque ID,
  effective_at?: RFC3339, observed_at?: RFC3339,
  claimed_actor_id: string, asserted_role: string, claimed_source_owner_id: string,
  claimed_provenance: bounded string, claimed_submitted_at?: RFC3339,
  reason_code: allowlisted value
}
```

Canonical request digest covers all fields; exactly one typed value **or** immutable document reference may be supplied according to a *future approved* source-category schema. No arbitrary SQL, filesystem path, URL fetch, uploaded bytes, free-text instruction, new policy rule or receipt may be interpreted as evidence. Limit size and redact sensitive fields; a document reference is only a pointer until an authorized owner verifies its origin, content, dates and allowed disclosure. The request must bind to the actual V1 original; candidate gaps need separate authorization/subject design, not silent treatment as original submissions. Reject unknown fields, duplicate IDs, wrong customer/line, future/backdated or conflicting source times, unsupported category/field, missing V1 checkpoint, changed pin/hash, and malformed types **before** any source operation.

```text
TrustedIntakeDecisionV1 { # emitted only by a separately approved authenticated service
  version, request_id, request_sha256, authenticated_actor_id,
  authorized_role_and_scope, authoritative_owner_attestation_id,
  trusted_received_at, validation_status: invalid | unverified | verified,
  disposition: rejected | pending_owner | accepted,
  reason_code, source_contract_version?, accepted_revision_id?,
  old_source_version?, new_source_version?, changed_source_ids?,
  intake_audit_id?, reviewer_visible_status
}
```

`accepted` requires `validation_status=verified` and is forbidden unless authentication **and** role/customer/field authorization, independent source-owner attestation, source schema/date/conflict/completeness verification and a durable source version readable under a compatible Phase 1C API all succeed. A rejected malformed request has `invalid`; a pending owner review remains `unverified`, **not** accepted. An intake decision records who authenticated/attested the change and the canonical payload digest; redact document/balance content from model logs. Persist rejected requests with sanitized codes under an approved retention/access policy, not raw secrets. No auth provider, source-owner identities, accepted source contract or persistence policy exists today, so the **only current runtime disposition is unavailable / not accepted**; do not treat a role string as a grant.

**Idempotency and conflicts (future gate):** atomically bind `(authenticated actor, original subject, idempotency key)` to canonical request digest and decision. Same digest returns the same decision/V2 ID without a second write or send; same key/different digest rejects `idempotency_conflict`. Distinct requests targeting the same `(source owner, source record, field, effective interval, parent source version)` serialize under a version compare-and-swap and reject conflicting concurrent revisions. An audit record alone, file `O_EXCL`, or SHA-256 digest does **not** implement authorization, concurrency-safe source updates or immutable source history.

## V1 → V2 lineage and reassessment design (blocked for runtime)

1. Validate a source-pinned V1 original with six fixed results and governed review via existing WP2 checkpoint/WP3 projection; it may have **completed or stopped AI stages**, including a reserved/uncertain send. Preserve its fixed results, reviewer package, candidate, AI/tool ledgers, reservations and receipts **unchanged**. A preflight failure without a pinned six-fixed original is *not* a V2 parent; handle it as a separate, freshly authorized submission path. Gap identity includes assessment/run/original subject, bundle/input digest, specialist, field, source/rule/line and code. A V1 reserved/uncertain send is terminal *for V1*; it must not be resumed. An interface limit is a request for a Phase 1C contract, **not** evidence that a user can supply a record.
2. Authenticate the actor externally, authorize source category/field/customer and obtain independently verifiable source-owner attestation. Reject unsupported fields; credit completeness, policy prerequisites, and withheld route roles have **no** trusted ingestible contract at this pin. Do not mutate the original submission or V1 bundle. If a salesperson revises the quote, follow the separately approved `supersedes_deal_id` new-submission path, not this evidence refresh.
3. Source owner issues a durable immutable revision/version (or an explicitly frozen, signed source snapshot readable by a **newly reviewed** Phase 1C reader contract) with old/new source fingerprints, changed record IDs, date/validity, provenance and conflict resolution. Attest that *all selected source families relevant to the run*, including independent credit/AR/payment, policy/routing and historical resolvers, have stable version semantics. **Historical V2 is blocked independently** until an explicitly approved pinned adapter/reader path can consume and replay frozen historical credit **and** operational manifests; simply signing one snapshot will not make the current adapter read it. Source version must be distinguishable from database transaction snapshot and business as-of. Phase 1C proposes a reader/release under a new exact SHA; perform the [separate compatibility and pin-approval gate](../planning/m22-scope-and-evaluation-design-2026-11-01.md#phase-1c-dependency-and-versioned-credit-adoption) rather than importing a development overlay. Old and new source snapshots must be independently replayable; reject unchanged/stale fingerprints and changed customer or original identity.
4. Only then allocate *new* Phase 1C run ID and Phase 2 assessment/thread ID; persist a versioned lineage record containing parent assessment/run/deal/pin/source/bundle, request/accepted revision IDs, new run/pin/source snapshot/bundle, changed refs, cutoff and separate checkpoint/receipt namespace. Persist/verify lineage and source acceptance **before** enabling any sender. No parent result, candidate, returned tool record, budget or receipt transfers into the new checkpoint. If new source is not released, no V2 is created.
5. Read V2 with the approved adapter inside a fresh read-only repeatable-read transaction; recompute all **six fixed specialists in sequence** including Routing on the same exact V2 original. Recheck source-version and selected-bundle identity after reading. Run six eligible original AI stages afresh **only if separately authorized** under new owner, quota and no-replay controls. Any new candidate is bound to V2 and has its own six fixed reruns and **fresh, V2-bound customer acceptance pending**. Create a new versioned human-only reviewer package comparing V1/V2: **no V1 human approval, exception, customer acceptance or route decision transfers to V2**; new human decisions require independent actor/role checks and version-bound audit. Checkpoint/restart must not produce a second V1 or V2 send for any uncertain request. No selective rerun until a reviewed dependency graph proves safe for Credit, Policy and Routing.

## Engineering feasibility and negative gates

| **A — safe now** | Source-contract audit, typed *design* and offline threat/negative-control plan; existing read-only WP3 gap projection, WP2 registry/checkpoint/receipt verification and original/candidate comparison. No accepted evidence or V2. A pure default-deny parser could be built later, but without an authenticator/owner or versioned reader it would not validate an accepted submission; this increment adds **no misleading executable acceptance prototype**. |
| **B — source owner/Phase 1C** | Assign stewards for each category and decide whether evidence can be ingested and durably versioned. | **C — authentication/human security** | Select authentication and trusted role/customer/field scopes, attest who may correct each domain, approval segregation, immutable audit and secure document store/retention. | **D — deferred** | Ingestion UI/API, source writes, V2 graph/sender, selective reruns, live provider campaign, held-out evaluation and any deployment. WP5 original M2.2 evaluation gate remains open independently. |

Required offline tests **after** B/C contracts are approved: unauthorized/forged actor and role, unknown customer/line/category, unsupported or malformed document/value/date, wrong V1/gap/source hashes, blocked candidate-origin misuse, duplicate identical key and conflicting key, concurrent source revision CAS, immutable V1 checkpoint and receipt after V2, new source version and genuinely changed bundle, full fresh six fixed and eligible AI stages, original/candidate separation, no retry of V1 unknown send, V2 restart/no duplicate send, human-only review. Test on new disposable PostgreSQL business/checkpoint databases using offline models. Mock authorization alone cannot prove a trusted live permission boundary. Until the interface exists these are **required future gates**, not passing tests or an implemented V2.

**Decision requested from Ali and Phase 1C/source owners:** Confirm the logical stewards and who authenticates/attests each category; identify whether an *existing* approved immutable source-release API is available or commission a separate Phase 1C source-version design; select an authentication/role and persistence boundary, with cost/security/learning implications, before authorizing any write or V2 runtime implementation. Recommendation: keep the current pin/read-only PostgreSQL; stage a reviewed source-version + trusted-auth contract first, then one supported category end-to-end with full six-check V2 under a new approved version. A direct SQL edit/overlay is easier but untraceable and unsafe; a new ingestion service/database adds operational cost and security surface and is **not** approved by this document.
