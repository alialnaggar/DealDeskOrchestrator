## Official Groq contract and attribution

Official [Qwen model listing](https://console.groq.com/docs/models) identifies a preview model with a 131,072-token context and 16,384-token maximum completion; the pilot's 512-token cap is below the model maximum. [Tool use](https://console.groq.com/docs/tool-use/overview) and [local tool calling](https://console.groq.com/docs/tool-use/local-tool-calling) list Qwen local function tools, `tool_choice="required"` and controllable `parallel_tool_calls`. Groq explicitly warns that `required` **can** return 400 if the model does not call any tool; whether that happened here is **unknown**. Tool schemas are object/array/string types with closed object definitions; no provider rejection identified any field or schema. [OpenAI compatibility](https://console.groq.com/docs/openai) says `temperature=0` converts to `1e-8`, so zero is **not confirmed invalid**. It lists `messages[].name` as unsupported, but the failed first request had no such field (only system/user messages). [Structured outputs](https://console.groq.com/docs/structured-outputs) lists Qwen strict JSON-schema support but forbids mixing structured outputs with tools; the failed inspection had **no** `response_format`. Final-schema incompatibility cannot explain the first POST because no final POST occurred.

Groq's [reasoning documentation](https://console.groq.com/docs/reasoning) says Qwen supports `none`, `default`, `low`, `medium`, `high`, that **raw** reasoning with tool use causes HTTP 400, and that `reasoning_format` should be `parsed` or `hidden` for tool calls. It also describes a compatible automatic default when tools are present: **the omission in the original request is not a proven defect or proven cause of the 400**. No raw setting was sent. Other possible causes (provider-side refusal of required tool use, tool-definition interpretation, model preview changes, or a provider validation error outside the allowlist) remain hypotheses. Do **not** label the observed 400 `tool_use_failed`, infer model quality, or relax validation on this evidence.

## Narrow preventive change, not a demonstrated live fix

Only Qwen Configuration's native-tool turns now explicitly set `reasoning_format="parsed"`; Groq documents this value as supported with tool calls. A separate `m20-qwen-configuration-tools-parsed-v1` **stage-wire identity** is bound in newly built manifests and Configuration model metadata while the existing system prompt, Pricing wire, strict no-tools Configuration final, 512/1,024 configured completion caps, source identity and rate budget are unchanged. A pre-send guard rejects a missing/raw reasoning format, any tool/structured-final combination, changed required-tool choice or parallel-call setting **before** a receipt reservation or sender callback; a graph checkpoint reservation may already exist and remains terminal. The existing request digest, manifest hash, exclusive owner, checkpoint and receipt gates still prohibit reuse of the old N01 request/assessment; historical GPT-OSS proposals are not changed. No provider claim is made that `parsed` alone resolves 400.

Offline tests construct the original seven-field shape and explicitly raw/unknown modes as **negative compatibility cases**, verify the parsed shape and unchanged strict final, and prove a tampered request cannot reach the sender or reserve a receipt.
