The existing `_claims`/typed terminal decoder still enforce exact returned ref, field, value and type. No new tool permission, business threshold, graph topology, candidate status, sender, provider or hosted budget changed. Existing replay of older completed inspections returns their originally recorded evidence; it does not fabricate the new view retroactively.

## M5 follow-up — offline Policy fixed-hit evidence (11 November 2026)

**Available versus unavailable authority:** The exact pinned Phase 1C decision carries selected `commercial_rule_hits` with `rule_id`, `area`, `severity`, and `scope` (`deal` or a deal-line ID). `specialists.policy.rule_hits` selects hits with `area=policy`, while `specialists.policy.hard_blocks` can also contain Credit/Pricing blockers. The selected `policy_rules` rows carry rule ID, set, area, severity, required action, scope type/value and a structured `condition_json`. The existing Policy AI tool already exposed selected hit-rule metadata, including `required_action`, `scope`, and `severity`, **but not a citable fixed result**; it did not prove non-hit rules passed or report underlying fact evidence references. Phase 1C's pinned policy interface has **no per-rule prerequisites, not-triggered/unknown status, or IDs for the source facts that caused each hit**. The rule's own ID and the subject scope are references to the selected rule and checked subject, **not proof of the underlying delivery/contract fact**. They must not be presented as source-document citations or a waiver.

**Implemented within the existing investigation:** For a synthetic B01 deal whose requested delivery is late, `m21_specialists.py` now adds an offline-only, versioned `policy_hit:PO-BASE-DELIVERY-LATE:M18-L-B01` record with exact `rule_id`, `subject_scope_ref`, `severity`, and `result="triggered"`. The associated `policy_rule:PO-BASE-DELIVERY-LATE` record supplies the actual selected rule's `required_action`. Multiple scopes may share one rule record, with each hit retaining its own scope; the rule record's legacy single-hit scope is omitted in the offline view to avoid a misleading global scope. Prior to tool disclosure, pinned identity, sealed fixed-decision run/deal/policy set, exact commercial Policy hit subset, mapped fixed Policy result, selected active matching rule and valid deal/line scope are checked. An already completed tool receipt is compared against that exact checked projection before replay. The existing ledger, exact returned-field claim validation, tool permission, checkpoint and reviewer authority remain unchanged. The model may cite a returned hit's triggered result and its returned rule's action; this is an **AI observation**, not a new rule evaluation. Zero hits produce **zero records**, not a `not_triggered`, `unknown`, or approval-ready finding. No invented explanation, external evidence ID or inferred prerequisite is exposed.

`m21_redaction.py` allowlists only the four fixed-hit scalar fields under an explicit `m5-policy-fixed-hits-offline-v1` view flag, checks that each hit references an actually returned matching rule ID/severity and only allows `result="triggered"`; deal scope is symbolic `deal` rather than leaking a raw subject ID. Without the flag an injected hit is rejected. Existing hosted Policy requests and their legacy projection/prompt/budgets are **unchanged**. New offline records are not retrofitted into older completed checkpoints.
