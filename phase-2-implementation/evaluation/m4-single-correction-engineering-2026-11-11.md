## Implemented versus already present

`fulfillment_correction.py`, `investigation_graph.py`, `live_models.py` and `candidate_graph.py` **already** implemented one narrow Fulfillment correction: an exact positive whole-unit string-format rejection or an exact pinned Phase 1C delivery-slice total mismatch. First raw result/failure remain in the checkpoint; feedback contains only bounded constraint code, field paths and at most 25 returned refs, not an answer key or a replacement schedule. The correction reserves a checkpoint attempt *before* the no-tools revised final, uses the same selected original evidence/subject, revalidates via the same contribution and candidate fixed-check paths, then stops. A reserved-only correction is terminal/uncertain on restart; already fixed-checked candidates remain unreserved and customer acceptance/human approval pending.

This increment adds `m4_correction_policy.py`, a shared six-responsibility **fail-closed eligibility decision** (not a send capability). Only Fulfillment's two already verified codes are eligible after a fully returned bounded result with remaining model turns. Configuration, Pricing, Credit, Policy and Routing are explicitly ineligible even for superficially similar codes: their typed terminal errors can collapse formatting, fabricated citations and semantic errors into a generic rejection, and their current hosted stage budgets/receipt protocols do not authorize a third send. `investigation_graph.py` now records the policy disposition for eligible and terminal Fulfillment cases; its first/revised attempt IDs bind assessment, Phase 1C run, subject/line, bundle/source digest, provider/model and specialist; the second ID also binds the first ID and distinct ordinal. It verifies saved status/identity/attempt count/ID before a resumed reserved or response-saved transition, records measured `elapsed_ms` for a returned or failed correction (not a synthesized provider latency), and preserves the original fixed results. Provider `model_attempt_ledger` remains the existing request reservation/usage record; the Fulfillment transport has **no independent receipt audit comparable to typed Configuration/Pricing/M2.1**, so do not present this checkpoint identity as provider-delivery proof. No hosted transport or stage budget was expanded.

**Example:** a ten-unit B01-like deal has eight stocked units and two confirmed inbound units. If the model writes `"8.000"` in a binding proposal, it is rejected, not silently coerced; a second *model-authored* `"8"` may pass the same source and fixed six-check candidate verification, still without reserving supply or approving customer terms. A different eleven-plus-eighteen overcount can receive only the exact bounded total constraint. This is not proof that an actual hosted model would self-correct.
