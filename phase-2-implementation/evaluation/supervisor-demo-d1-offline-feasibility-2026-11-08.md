# D1 — RC01/B01 offline feasibility (8 November 2026)

**Verdict: feasible as an offline integration test, not yet an operator-ready live demo.** One fresh assessment can execute six **original-subject** AI stages with scripted transport responses, one Fulfillment binding candidate, six **candidate-subject deterministic** rechecks and a human-only review. This is not six candidate AI reruns, not independent accuracy evidence, and not a repeatable hosted-provider reliability claim. No hosted request was made for this audit; no production or held-out data was changed.

## Frontend-safe projection and D2 recommendation

Expose **only a validated, authenticated, assessment-scoped, server-allowlisted projection**: assessment ID and pinned source identity/hash/as-of time; synthetic deal/line summary (quantity, requested date, partial permission); per-specialist fixed finding and separately labeled AI execution/validated claim `{ref, field, value}` with citation to an authorized returned record; supported Fulfillment proposal slices, tradeoff, pending acceptance and exact candidate ID; six candidate **fixed** statuses with original/candidate subject labels; unresolved evidence gaps with provenance/verification; review status, withheld-routing flag and human-only action. Include explicit `offline_scripted`/`hosted` execution label and a disclaimer that returned source evidence is not stock reservation or complete ledger coverage. Never suggest Policy non-hits are evaluated or withheld Routing roles are empty. Do not display accuracy or estimated costs when absent.

Technical progress may publish *sanitized* graph stage/attempt status, checkpoint position, allowed tool name, count of inspected records, bounded error category, elapsed time if available, and `reserved`/`returned`/`uncertain` distinction. Correlate all events by one assessment ID and monotonic sequence. Do **not** send raw checkpoints, sealed bundles, complete deal/customer/credit records, AR invoice numbers, payment identifiers, untrusted model text, rejected claims, prompts, secrets, request bodies, owner/receipt file paths, database DSNs, private manifests or provider diagnostic bodies to the browser. `m22_capture` and the reviewer package are **validation inputs, not public JSON schemas**: the package's `returned_source_provenance.fields` and fixed payloads require field-level minimization and role-aware access; citation refs themselves can encode source IDs. Receipt reconciliation stays server-side and must not be inferred from capture alone.

**Minimum D2 backend:** (1) a dedicated, explicitly offline, fresh-assessment execution service wrapping the existing `_six_campaign` sequence without importing test fake-POST monkeypatches into production or allowing the hosted CLI to be called accidentally; dependency-inject scripted offline model transports behind the existing provider boundary; (2) exclusive disposable DB preflight, pinned Phase 1C and RC01 overlay provisioning/verification, fresh ID/thread, durable checkpoint and no-replay receipts; (3) authenticated/authorized run-scoped Python endpoints, e.g. `POST /demo/assessments` (development-only, fixed case/variant allowlist, mode `offline_scripted`, idempotency key, no arbitrary source writes), `GET /demo/assessments/{id}` (status/last event), `GET /demo/assessments/{id}/events?after=seq` (poll first; SSE only if warranted) and `GET /demo/assessments/{id}/review` (available only after validated handoff). All are read-only *against business evidence* apart from the explicit create/run operation in disposable demo databases; no approval, reservation, waiver or candidate acceptance endpoint. (4) server-side `capture_m22`, `project_gap_review`, checked candidate validation and private receipt reconciliation before constructing a versioned, allowlisted DTO; terminal/uncertain states remain visible without replay. (5) append-only progress projection at persisted graph/checkpoint and send-boundary events, with monotonic event IDs, explicit `preflight/running/stopped/completed`, separate AI/fixed stages and restart-safe cursor. Polling a final checkpoint alone cannot provide live progress. A deployment/authentication/network boundary and Next.js integration contract must be reviewed before any UI is built; no new framework or billable provider is implicitly approved by this report.

**Remaining blockers:** no ready-to-call offline single-assessment operator CLI/API, no supported event stream or authenticated API, no Next.js UI, no independent accepted answers and no basis for hosted success-rate/accuracy claims. The private historical Groq outcome has not been reproduced with a live model and must not be presented as a fresh run. Later paid/provider calls need separate approval; Phase 1C source pin/limitations, original/candidate isolation and human-only authority remain unchanged.
