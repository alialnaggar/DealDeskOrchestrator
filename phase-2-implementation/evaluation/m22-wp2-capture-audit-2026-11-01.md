## WP2 bounded offline receipt follow-up (after Week 4 extension plan)

`backend/dealdesk_phase2/m22_receipt_audit.py` is a **separate read-only reconciliation**. Given a pinned completed/stopped checkpoint and an explicitly caller-approved, owner-only temporary root, it reuses `capture_m22` and existing `verify_receipt` without invoking a sender or modifying the audit. It checks recorded owner device/inode and exact manifest or typed protocol digest, then pairs each receipt-bearing Configuration/typed Pricing/M2.1 reservation to its stored request digest, stage and ordinal. A valid returned marker must agree with a returned checkpoint row; a reserved-only or failure marker is `unreturned_or_uncertain`, **not** proof of provider non-delivery. Missing, tampered, wrong-owner or disagreeing receipts fail closed. The checkpoint-only capture deliberately remains `not_checked` so readers cannot confuse the two. Fulfillment's separate iterative model-attempt ledger and any M2.0 transport without a receipt remain `not_verified_by_this_projection`; it cannot report end-to-end receipt verification or safe replay.

Existing offline six-stage campaign cases now check 10 receipt-bearing reservations (Configuration 2, typed Pricing 2, M2.1 6) in each of five candidate/no-candidate fixtures and compare the same reconciliation after PostgreSQL restart without sending again. A disposable candidate test rejects wrong manifest digest, owner root and tampered M2.1/typed-final receipts. The existing HTTP 400/transport-timeout/crash stopped case now also tests HTTP 429 and checks one unreturned Credit marker after restart; local pre-send quotas and legacy/failed/reserved-only receipt format remain separately covered by `test_groq_dev_rate.py` and `test_hybrid_send_reservation.py`. These do **not** estimate hosted reliability or assert that historical external receipts were reconciled on this host.
