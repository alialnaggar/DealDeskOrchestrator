## Question, method and evidence

M1.8's four live Groq candidates had JSON strings like `"8.000"`. The opt-in provider schema specified `type: string`, so Groq complied with its schema; the V3 trusted contract in `backend/dealdesk_phase2/candidate_contract.py` correctly rejected anything other than a positive ASCII whole-unit digit string. The adapter's `_canonical_final` passed model content through without reformatting. The cause was a mismatch between permissive *provider output schema/instructions* and strict *trusted proposal validation*, not a failure of the Phase 1C verifier. The source reader itself serializes a whole quantity as Decimal `8.000`, which the model may copy verbatim. The historical four failures remain in `m1.8-live-observations.json`; they are not recoded as successes.

The repair changes only the opt-in binding prompt and schema **description** in `backend/dealdesk_phase2/live_models.py`, with a versioned suffix. It asks for e.g. `"8"`, never `"8.000"`, a JSON number or rounded fraction; the second version explains that source `8.000` can represent eight whole units without relaxing the output contract. The program still does **no automatic normalization**, rounding or date/source change. The raw action is checkpointed, malformed model content stays in the audit, and Phase 1C alone decides proposed quantity, date, source-to-slice and business validity. The claim-only M1.6 prompt, source permissions, candidate identity and original assessment are unchanged. The schema description is guidance, not a validation guarantee; the V3 validator remains authoritative.

The compatibility diagnostic `backend/dealdesk_phase2/compat_m19.py` uses separate subprocesses, each importing one exact Phase 1C checkout, and read-only repeatable-read transactions against the *same disposable PostgreSQL rows*. The existing CI first loads the pinned schema, 14 reference fixtures, compiled rules and nine isolated Phase 2 evaluation cases. The diagnostic compares 14 reference runs plus B01/B05, selected reader field/type shapes, source digests, six-domain fixed values, aggregate statuses and binding candidate outcomes. It writes an expiring full CI artifact and a committed compact observation summary. No development-branch Python module enters the production pinned adapter. Some data/modes beyond these 16 observations remain untested.

### Ownership and read-only mapping

| Concern | Owner and contract |
| --- | --- |
| Business evidence, as-of selection, catalogue/policy rules, quantities, dates and candidate validity | Phase 1C dated reader and deterministic functions. Phase 2 receives an exact sealed source pool through its read-only pinned adapter and rejects digest or identity mismatches. |
| AI investigation, permissions and citations | Phase 2 LangGraph and trusted tool adapter. A model citation must match a record actually returned within the pinned assessment, not merely an ID existing in the database. Phase 1C's known-reader-ID envelope check is narrower. |
| Run identity and persistence | Phase 1C run/deal/as-of/config/policy/catalogue identify the source; Phase 2 assessment/thread and candidate ID identify graph execution and subject. Phase 2 PostgreSQL checkpoints own model/tool attempt ledgers and restart budgets. Phase 1C's `agent_execution_log` writer is an independent deterministic development proof; no dual write or shared retry owner is authorized. |
| Original, candidates and reviewer decision | Original submitted deal never changes. Phase 2 stores each unverified AI hypothesis and its fixed Phase 1C recheck separately, compares outcomes and prepares human review. Customer acceptance, reservations and business approval are never granted by either runtime. |

Read-only status crosswalk: Phase 1C execution `Success` means its deterministic development writer persisted an envelope; Phase 2 `completed` means a graph responsibility ran. Neither implies business `supported`, Phase 1C `approval_required`, Phase 2 `fixed_checked` or a human approval. A Phase 1C candidate `supply_supported_unreserved` is structural supply evidence, while its aggregate `needs_revision` explicitly retains customer acceptance. Phase 2 `fixed_rejected` means a proposed candidate failed deterministic checking; the original finding remains independently available. Citation mapping must retain source category/ID, date/commitment status and Phase 2's returned-by-authorized-tool ledger; a bare reader ID is insufficient model-grounding evidence. Phase 1C required roles are empty when routing is withheld; Phase 2 reports them unavailable rather than fabricating a hypothetical route.

## Limitations and next gate

The diagnostic covers 14 reference runs and two related synthetic binding cases; it does not test every historical/v2 source, digital/provider path, nonempty component offer, approved answer, write interoperability or a resumed checkpoint under a new Phase 1C pin. A reader-only additive field can change a sealed bundle hash even when the source input digest and decision stay unchanged. Future pin adoption therefore requires new versioned assessment context and explicit approval, not an in-place checkpoint replay. The source-first 36-case independent review and Phase 1C runtime-output field gate are still open. The conditional 20-unit 12+8 supplier-offer idea remains unsupported by the binding verifier.

M1.9 is complete as a bounded contract repair, compatibility measurement and documented negative live validation. It establishes a tested prompt/strict-output boundary and a measured cross-branch compatibility gate. It does **not** establish useful live AI candidate quality. Configuration and Pricing AI are the recommended next *separately approved* milestone: first bounded evidence-grounded investigation and typed findings under fixed Phase 1C authority, with no substitution or repricing commitments. Any future normalization rule, Phase 1C pin change or further live Fulfillment trials needs a separate explicit decision.
