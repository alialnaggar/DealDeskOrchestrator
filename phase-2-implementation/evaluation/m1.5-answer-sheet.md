## Review method and boundaries

1. Read the pinned `phase-1c-data/implementation/test_phase1c_reader.py` reference expectations and the real selected-source projections in `backend/dealdesk_phase2/fulfillment_tools.py`; record the deal, dated evidence, fixed result, customer permission, and forbidden claims **before** inspecting live model output.
2. Keep this answer sheet outside the restricted Fulfillment input and every provider request. Tests read it for assertions; models receive only the pinned input and authorized tool observations.
3. Treat real reference, synthetic offline bundle, and fault injection as **three separate categories**. Synthetic bundles test Phase 2 behavior, not accepted Phase 1C ground truth. The source-only reviewer checks semantic claims in each live final payload; valid JSON and valid citation IDs alone do not establish truth.
4. For each result record evidence hashes, returned tool references, model/provider/version, prompt, token usage, elapsed time and API errors. A business claim is supported only when the cited *returned* record actually entails it under the fixed reader; do not infer unseen supply from the bounded selected pool.
5. Count critical failures separately: invented confirmed supply or delivery commitment, unseen or unauthorized citation, unauthorized access, altered original/fixed result, or ordinary approval granted by AI. A single such failure blocks any claim of readiness. No aggregate accuracy across the three categories.
6. Before reporting a scored result, compare its free-text finding, tradeoffs, assumptions and unmet requirements with source evidence and the fixed finding. Automatic checks cover structural invariants, source access, budget and some prohibited structured claims; they cannot establish general semantic correctness of prose.

## Scoring and stop conditions

Report per-case fixed outcome, AI gate, tool requests/results, citation validity, output contract status, independently reviewed semantic correctness (pass/fail/unreviewed), appropriate abstention, critical incidents, latency and tokens. Summarize **within** each case category only; a run skipped by the AI gate cannot be an AI success. Zero critical incidents is necessary but not sufficient for a quality claim. Any unreviewed prose stays `unreviewed`; a successful API request is not a business-correct answer.

Only R03 currently has a previously demonstrated eligible Groq live investigation. Run at most one new eligible R03 Groq trial and one R01 no-AI control in the bounded M1.5 validation. This measures reproducibility and concrete source interpretation on one actual business case; it cannot measure diversity or superiority over Gemini. More distinct real AI-eligible cases require separately reviewed compatible data and, for mixed delivery validation, Phase 1C-owned fixed-interface work.
