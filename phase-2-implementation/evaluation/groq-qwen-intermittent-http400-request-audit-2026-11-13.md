**What an HTTP 400 diagnostic can and cannot show:** The development transport already calls `_post(..., classify_transport=True, reject_redirects=True, capture_http_error=True)`. On an HTTP error it reads at most **1,025 bytes**, rejects bodies over **1,024**, and retains only allowlisted `error.type` (`invalid_request_error`/`api_error`), `error.code` (`invalid_request_error`/`tool_use_failed`/`json_validate_failed`), `error.param` (including `tool_choice`, `tools`, `messages`, `max_completion_tokens`), or a canonical UUID `x-request-id`; it **never stores** raw text, messages or bodies. A recognized `tool_use_failed`/`tool_choice` mock is classified and stored only as categories, and an unrecognized code/param or oversize response is suppressed in offline tests. All historical HTTP 400 receipts contain **no allowlisted diagnostic**. The bodies are gone; no retrospective classification or assertion that `tool_use_failed` occurred is possible. Groq's [error documentation](https://console.groq.com/docs/errors) guarantees an error object with `message` and `type` in its example, but does not guarantee an allowlisted `code`/`param` or a ≤1,024-byte response. Absence of a captured category cannot distinguish unsupported provider fields, model-generated invalid tools, an oversized/non-JSON body, or other provider failure; do not persist arbitrary messages merely to learn the reason.

**Attribution and next live experiment:** The first two `required` failures are consistent with Groq's [documented possible 400 when a required tool is not called](https://console.groq.com/docs/tool-use/local-tool-calling), but no error code confirms that explanation. The later `auto`/parsed inspection failed even though its fixed schema/settings and plain-N01 source context had already yielded a returned inspection; this rules out a reproducible *fixed* invalid schema or a universally rejected auto/parsed configuration. Possible model/provider nondeterminism, request-identity sensitivity and a provider validation behavior not covered by the diagnostic allowlist remain **unverified hypotheses**. Do not change schema, prompt, temperature, token caps, evidence validation or rate policy from these data. **If** further hosted testing is later desired, wait for provider cooldown, verify Free-plan and model/account quota again, then make exactly one *new* isolated N01 Configuration-only assessment with the existing auto/parsed wire and diagnostics; stop at the first failure, do not replay or enable a correction loop for it, and inspect only the new allowlisted receipt. If that yields another blank 400, obtain provider support/console assistance through an owner-approved private channel rather than repeated blind sends. Only a confirmed completed Configuration trace can precede a new Pricing test; no inference is authorized by this audit.
