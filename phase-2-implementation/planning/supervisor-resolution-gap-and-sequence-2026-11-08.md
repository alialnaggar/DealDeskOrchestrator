## Proposed M5 contract and dependency review (NOT implemented here)

**Recommendation:** solve RC01 first with its honest, supported Fulfillment V1 and a source-derived explanation of unmet customer requirements; do not spend an M5 multi-agent rewrite to "fix" healthy Configuration/Pricing/Credit. For broader cases, if Ali approves a bounded pilot, add capabilities incrementally on the current Python/LangGraph/PostgreSQL stack, not a new orchestration framework or source store. The M5 draft is estimated **8–16 engineering days plus source-owner review** for a narrow compatible-source pilot; a full multi-domain production composer, trusted evidence intake and candidate-specific hosted execution are **not estimated or authorized** until Phase 1C capabilities/security/owner decisions are resolved. This is an engineering planning range, not a promise.

Rough pilot breakdown (subject to allowed-source review): 1–2 days contract/permission inventory, 2–4 days conflict-aware composer, 2–3 days lineage/checkpoint/receipt boundaries, 2–3 days candidate-scoped offline reassessment, 1–4 days fault/regression and review. If the required product/price changes are not supported by the pinned reader, **stop** at the contract review; any Phase 1C upgrade is a separately estimated and authorized project, not hidden inside the 8–16 days. There is no new paid runtime or infrastructure in this proposal; implementation still consumes engineering time and increases checkpoint/security surface versus deferring M5. The safer alternative is to keep one Fulfillment V1 plus human review while M3/M4 and accepted answers progress.

Proposed types (names/signatures provisional): `SpecialistRecommendationV1 {assessment_id, subject_id, specialist, action_code, explanation_code, source_refs, rule_ids, confidence_scope, verification='suggested_unverified'}`; `ActionableProposalV1 {assessment_id, source_bundle_sha256, parent_subject_id, specialist, allowed_field_changes, prerequisite_fingerprints, cited_returned_refs, model_prompt_contract_versions}`; `CandidateRevisionV1 {candidate_id, parent_subject_id, lineage_ordinal, exact_field_changes, source_input_digest, candidate_input_digest, proposal_refs, fixed_results_by_specialist, customer_constraints_unmet, status}`. Trusted runtime—not the model—assigns identity, producer, digest, verification and status. Authoritative business eligibility/values remain in the pinned reader and fixed verifier. JSON fields must be closed/typed and strict about unknowns; no Pydantic migration or framework is implied.

Dependency map to review: Configuration change invalidates Pricing → Fulfillment → Credit (only if commercial value/terms change), Policy and Routing; Pricing change invalidates fixed commercial values → Credit, Policy and Routing; Fulfillment schedule change invalidates delivery Policy and Routing (and Credit only if terms/exposure change). **Regardless of AI dependency selection, rerun all six deterministic candidate checks** on each exact Vn; candidate AI tools are default-deny until expressly scoped. Source fingerprints must include pin, sealed bundle/source digest, parent subject, changed fields and returned tool refs. A stale/changed source needs a new authorized assessment, not a blind retry. Customer acceptance is an external trusted workflow state, never an AI conclusion.

Proposed sequence/gates: (1) land narrowly safe reliability fixes and decision regression; (2) add source-grounded original/revised comparison and human recommendation projection **without changing rules**; (3) review Phase 1C candidate allowed fields and safe proposal schemas with Ali/source owner (stop if incompatible); (4) independently test conflict-aware composer + V0/V1/V2 lineage on synthetic development fixtures, full six fixed reruns and rollback-free restart; (5) review/re-authorize candidate tool scopes and selective AI dependency fingerprints with negative tests; (6) only after (3–5) review operator API and Next.js; (7) hosted execution solely after its distinct security, answer-readiness, provider and budget authorization. Each stage has tests for forged refs, changed digest, conflict, stale source, uncertain send, candidate/original cross-talk, reviewer gate and human-only acceptance. Do not merge an unfinished Phase 1C draft or add a writable source evidence API under this proposal.

**Decision requested before architectural work:** authorize (or defer) a bounded M5 V0→V1→V2 pilot, exact Phase 1C candidate-change surface, candidate-subject tool/read boundary, and whether customer acceptance will be handled only as an external handoff. Separately review the M4 correction-turn design and any hosted-path trust implementation. Until then, the safe single-candidate V1 path is a valid and meaningful, but explicitly unresolved, revised-offer demonstration.
