## What the source and reader actually prove

The [pinned v2 source definition](../provisional_cases.json) has 36 cases and 36 distinct case customer IDs. Each case has exactly one `customer_credit_profiles` row. **None of the 36 case `tables` objects contains an `accounts_receivable` or `payment_history` key or row**. The [generator](../../implementation/render_phase1c_evaluation_cases.py) constructs the credit profile, but never adds either table. The [v2 index](../provisional_packet_index.json) pins source-definition SHA-256 `1b7e0dffb3eaae8ee7c7e4bcd82aba0d55da11321198ce8c54e1581fae6740cc`. Prior two-pass PostgreSQL replay verified the resulting 36 source/provider pairs at [PR run 39890202053](https://github.com/alialnaggar/DealDeskOrchestrator/actions/runs/39890202053); no new database run was made for this audit.

For nonhistorical runs, [`read_run`](../../implementation/phase1c_reader.py) selects one credit profile, the latest eligible AR row **per invoice**, and payment events dated no later than the run cutoff. It returns `receivables=[]` and `payments=[]` when those queries select none. The current numeric exposure formula adds the quoted deal total and unbilled commitments to the sum of **selected** AR; that empty sum is zero. The 24-hour freshness flag applies to `commitments_as_of_at`, not to completeness of the AR or payment populations. A repeatable-read database transaction seals the selected view; it does not establish that every relevant invoice or payment was loaded. [The reader coverage record](../../implementation/phase1c_reader_coverage.md) explicitly states that a missing invoice or source-wide completeness marker cannot be detected with the current schema.

Historical runs have a stronger, separate rule: [`select_historical_credit`](../../implementation/phase1c_historical_credit.py) requires a matching cutoff, customer and snapshot ID plus `complete is True`, a matched commitment proof, and explicitly supplied `receivables` and `payments` arrays. There, a validated empty array in a complete manifest can represent zero **recorded** items within that synthetic snapshot. The historical completeness rule is **not** automatically inherited by nonhistorical v2 evaluation inputs or Phase 2's B01 fixture.

The [approved v2 business contract](../../implementation/phase1c_evaluation_business_contract.json) specifies a 24-hour maximum for credit-commitment observations. It does **not** declare a complete AR/payment snapshot for the 36 evaluation cases. A review aid refers to a “fictional complete-snapshot assumption,” but that wording is not a versioned source-wide completion fact in the packet or contract. Consequently, it cannot by itself substantiate a complete-zero claim.
